# Database schema

SQLite at `/opt/data/finance/tally.db` (on the host: `data/finance/tally.db`).

Use this only for queries the CLI does not cover. For anything a subcommand
handles, **use the subcommand** — it validates input, handles the timezone and
keeps integrity. Raw SQL validates nothing.

Never write through SQL. Hand-written `INSERT`/`UPDATE`/`DELETE` bypass the
validations and produce rows the reports cannot interpret.

## Conventions

- **Money:** integer cents, always positive. `2750` is R$ 27,50. The `type`
  column decides the direction, not the sign.
- **Dates:** `YYYY-MM-DD` text, in `America/Sao_Paulo`.
- **Timestamps:** ISO-8601 with offset.
- **Booleans:** integer 0/1.
- **Language:** identifiers are English; the *values* in `categories.name` and
  the seeded account are Portuguese, because the user reads them.

## Tables

### `transactions` — the core ledger

| Column | Type | Note |
|---|---|---|
| `id` | INTEGER PK | The number the user sees and quotes to correct something |
| `type` | TEXT | `expense` \| `income` \| `transfer` |
| `amount_cents` | INTEGER | Always > 0 (CHECK) |
| `description` | TEXT | Required |
| `date` | TEXT | When it happened, not when it was recorded |
| `category_id` | INTEGER FK | NULL on a transfer |
| `account_id` | INTEGER FK | Source account |
| `dest_account_id` | INTEGER FK | Transfers only; required there (CHECK) |
| `note` | TEXT | |
| `source` | TEXT | `telegram` \| `recurring` \| `cron` \| `import` |
| `recurring_id` | INTEGER FK | Set when generated by a fixed cost |
| `installment_num` / `installment_total` | INTEGER | `3` and `12` in "3/12" |
| `installment_group` | TEXT | Same hash across every instalment of one purchase |
| `created_at` / `updated_at` | TEXT | |

### `accounts`

`id`, `name` (unique), `type` (`checking`, `card`, `cash`, `savings`,
`investment`, `voucher`), `institution`, `closing_day`, `due_day`, `limit_cents`,
`opening_balance_cents`, `active`, `created_at`.

A deactivated account (`active = 0`) drops out of listings but keeps its history.

### `categories`

`id`, `name`, `parent_id` (NULL = root), `type` (`expense`, `income`, `both`),
`emoji`, `active`. Unique on `(name, parent_id)`.

Two levels deep. Filtering or budgeting a root includes its children.

### `budgets`

`id`, `category_id` (**NULL = the month's total cap**), `month` (`YYYY-MM`;
**NULL = applies to every month**), `limit_cents`, `alert_pct`, `created_at`.

When both exist for the same category, the month-specific one wins.

### `recurring`

`id`, `description`, `type`, `amount_cents`, `category_id`, `account_id`,
`frequency` (`monthly`, `weekly`, `yearly`), `day`, `next_date`, `ends_on`,
`active`, `created_at`.

`recurring apply` generates transactions up to today and advances `next_date`. It
is idempotent per `(recurring_id, date)`.

### `goals`

`id`, `name` (unique), `target_cents`, `saved_cents`, `deadline`, `active`,
`created_at`.

### `tags` and `transaction_tags`

Many-to-many. `transaction_tags` cascades when a transaction is deleted.

### `sent_alerts`

`(key, month, level)` as the primary key, plus `sent_at`. This is what stops cron
from warning twice about the same limit. `level` is `warning` or `over` — moving
from one to the other counts as a new alert.

### `settings`

Key/value pairs: `currency`, `timezone`, `default_account`.

### `schema_version`

One row per applied migration. It is what makes `init` safe to run every time.

## The `v_transactions` view

Joins already resolved — query this, not the raw table:

`id`, `type`, `amount_cents`, `description`, `date`, `note`, `source`,
`installment_num`, `installment_total`, `installment_group`, `recurring_id`,
`created_at`, `updated_at`, `category_id`, `category`, `parent_category`,
`category_emoji`, `account_id`, `account`, `account_type`, `dest_account_id`,
`dest_account`.

## Example queries

To run a read-only query:

    node --input-type=module -e "
    import { DatabaseSync } from 'node:sqlite';
    const db = new DatabaseSync('/opt/data/finance/tally.db');
    console.log(db.prepare('<SQL>').all());
    "

Do not pass `{ readOnly: true }`: the database is in WAL mode, and a read-only
connection fails when the `-shm` file does not exist (it is not allowed to create
one). Safety comes from running only `SELECT`.

**Spending by day of week** (0 = Sunday):

    SELECT strftime('%w', date) AS dow, SUM(amount_cents)/100.0
    FROM transactions WHERE type='expense'
    GROUP BY dow ORDER BY dow;

**Most frequent merchants:**

    SELECT description, COUNT(*) n, SUM(amount_cents)/100.0 total
    FROM transactions WHERE type='expense'
    GROUP BY LOWER(description) HAVING n > 2 ORDER BY total DESC LIMIT 10;

**Month-over-month trend:**

    SELECT substr(date,1,7) month,
           SUM(CASE WHEN type='expense' THEN amount_cents ELSE 0 END)/100.0 out,
           SUM(CASE WHEN type='income'  THEN amount_cents ELSE 0 END)/100.0 in_
    FROM transactions GROUP BY month ORDER BY month;

**Instalments still to come:**

    SELECT description, installment_num, installment_total, date, amount_cents/100.0
    FROM transactions
    WHERE installment_total IS NOT NULL AND date > date('now','localtime')
    ORDER BY date;

## Migrations

Defined in `scripts/db.ts`, in the `MIGRATIONS` array as `{version, sql}`. To
evolve the schema: append a new entry with the next version — never edit one that
has already been applied — and run `fin.ts init`.
